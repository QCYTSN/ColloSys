## 2. 第一阶段：把第三方登录的配置和真实可用性处理完

### 2.1 先查实际配置

读取本地已有授权配置与后端环境，
仅输出配置是否存在、服务地址与健康状态。

检查：

- AUTH_GITHUB_ID / AUTH_GITHUB_SECRET
- AUTH_GOOGLE_ID / AUTH_GOOGLE_SECRET
- SITE_URL、当前 Convex callback origin
- 桌面 beginSignIn、系统浏览器地址和本机回调服务
- 当前账号映射与邮件密码登录状态。

依照现有认证 SDK 的当前官方文档，
核对 provider checks、回调注册及服务端交换方式。

继续使用现有 Convex Auth 与桌面领取流程。

本地文档中的端口3407/3409是当前配置线索，
最终控制台回调必须与实际运行服务完全一致。

开发客户端和生产客户端分别配置。

已有可用凭据时完成两家真实授权。

缺少时立即给出一次集中配置交接：

- 提供商后台入口。
- 客户端类型。
- 准确回调地址。
- 所需权限。
- 密钥写入的本地文件或后端位置。
- 重新加载命令。

密钥通过本地配置或后端 secret 管理器输入，
不要求粘贴到聊天。

同一轮继续完成其余代码、状态、画面与隔离验证；
真实提供商往返保留为明确的外部配置项。

后续配置到位，运行同一条验证入口即可继续，
不需要再次改 UI。

### 2.2 提供商能力成为正式 UI 状态

把以下状态分开：

- checking：正在读取服务能力。
- ready：服务配置齐全，可以发起。
- unconfigured：服务明确未启用。
- temporarily-unavailable：配置读取或服务暂时失败。

ready 只表示可以发起，
不表示已经证明本次登录成功。

界面不显示未经验证的“已连接”。

未启用的提供商保留品牌入口，但标明“未启用”；
提供常驻、简短说明和独立的配置帮助入口。

按钮不得伪装成正常登录，
错误也不能只靠鼠标 tooltip 才可发现。

可恢复读取错误显示“重试检查”，
不误报成永久未配置。

配置改变后能刷新能力，无需重建整个表单。

面向普通用户的提示采用：

“此服务暂未启用 Google 登录。”

面向开发者的诊断说明缺少哪个配置项。

长技术信息进入可展开诊断区域，
主表单只显示能指导下一步的一两句。

### 2.3 真实流程

每个 provider 都验证：

1. 从正常桌面入口点击登录，系统浏览器打开正确授权页。
2. 授权结果在服务端核验，用户明确批准本次桌面请求。
3. 桌面一次性领取，建立现有 ColloSys 会话。
4. 进入原请求的合法项目/页面。
5. 退出、重新打开和重复登录正确。
6. 取消、拒绝、超时、重复回调、过期请求和退出后的迟到回调有正确结果。

保持最小权限：

GitHub 身份登录与仓库授权分开；
Google 身份登录与其他 Google 数据权限分开。

所有 client secret 和提供商长期 token 留在受控后端。

桌面回跳只携带现有一次性请求标识；
日志、地址栏、录像和打包文件不含凭据。

## 3. 第二阶段：已有账号能够安全关联 GitHub/Google

当前“相同邮箱拒绝自动合并”的保护继续保留，
同时补齐正式关联能力。

### 3.1 产品入口

在账户设置增加“登录方式”：

- 邮箱密码：是否已设置。
- GitHub：未关联 / 已关联的账号名称。
- Google：未关联 / 已关联的账号标识。
- 关联、重新验证和适用的解除关联操作。

现有邮箱账号从这里主动关联。

登出状态下遇到相同邮箱冲突，
提示先用原方式登录再关联，
不重复注册、不静默合并项目与数据。

### 3.2 服务端关联契约

先检查现有 SDK 的安全账号关联能力。

可以直接复用时按其契约接入；
需要自有协调逻辑时，
仍使用既有 auth account 映射和会话体系。

关联尝试必须由已认证用户发起并绑定：

- 目标内部用户 ID。
- 提供商及 purpose=link。
- 本次请求、有效期、一次性挑战。
- 当前会话/身份代际。
- 原登录方式的近期重新验证事实。

目标用户从服务端会话得到，
不接受浏览器任意提交目标 ID。

第三方身份按 provider＋稳定 subject/user ID 识别，
不按邮箱或显示名识别。

同一提供商身份已属于另一内部账号时，
拒绝关联并给出可操作说明。

账号绑定与唯一性检查事务化，
重复回调保持幂等。

桌面与系统浏览器可能登录不同内部账号。

回调必须遵守本次服务端绑定的关联主体与授权证明，
不以浏览器当前账号覆盖桌面目标，
也不把现有其他账号数据迁移过来。

解除关联要求重新验证，并确保还存在至少一种
经过验证、当前可用的登录方式。

解除最后一种登录方式应被后端阻止，
而不只是前端隐藏按钮。

### 3.3 验证

使用隔离账号验证：

- 邮箱账号关联 GitHub 后，
  退出再用 GitHub 回到同一个内部用户和同一组项目。
- Google 同样验证。
- 同邮箱但未关联的身份仍不能自动接管账号。
- 已被另一账号使用的 provider identity 不能被抢占。
- 关联中退出、换号、过期、重复回调不造成错绑。
- 解除之后映射正确，最后一种登录方式受到保护。

外部配置未就绪时，
完成受控回调和后端权限测试；
真实 provider 往返单列待完成。

## 4. 第三阶段：所有登录方式共享一个认证事务

在现有认证结构里建立统一协调状态，
不再让邮箱和 OAuth 各自决定自己是否忙碌。

状态至少表达：

idle
→ initiating
→ awaiting-provider / submitting
→ establishing-session
→ succeeded

以及：

cancelled / failed / expired。

每次尝试记录 attemptId、method、generation。

密码和 provider secret 不进入共享状态、
日志或持久化 UI 数据。

### 操作规则

- 首次点击同步取得提交锁，
  同一帧连续点击也只启动一次。
- 邮箱提交时禁用其他登录入口；
  OAuth 发起和等待时禁用邮箱提交及另一个 provider。
- 当前操作的取消、重试入口保留。
  取消能够取消的 OAuth attempt；
  对已经不能撤销的服务端步骤，准确展示状态。
- 输入草稿保留。
  提交中的相关字段锁定或按已有版本机制保护，
  响应不能覆盖后续新输入。
- 只有当前 attempt 和 generation
  可以改变 UI 或触发导航。
- 退出、换号、离开认证路由后，
  迟到结果不能复活旧会话或覆盖新尝试。
- 成功事实来自验证后的 ColloSys 会话，
  不来自浏览器已经打开、OAuth promise返回或动画结束。

检查邮箱 hook 的 leaveTo、
页面 router.replace、
OAuth complete 和 startup effect
是否同时负责导航。

明确一个认证完成入口，
其余路径只上报结果，
避免一次成功重复刷新或跳转。

组件卸载和重挂载不能重新发起登录。

取消后的错误回包不覆盖新的正常表单。
return_to 沿用已验证的内部目标规则。

必须用可控慢请求测试：

- 邮箱提交时点Google。
- GitHub连续双击。
- GitHub等待时切Google。
- 取消后立即重试。
- 退出后旧回调成功。

断言实际请求数和最终内部用户，
而不只检查按钮颜色。

## 5. 第四阶段：登录页的布局不随错误上下漂移

沿用宽屏左54%/右46%、
窄桌面48%/52%的整体关系。

右侧表单最大宽368px，
输入和主要按钮44px高。

Google Sans与Newsreader的已验证角色继续使用。

### 5.1 固定表单起点，而不是动态内容整体居中

右侧改为从稳定起点向下排布：

- 宽屏 padding-top 初始值：
  clamp(80px, calc((100svh - 560px) / 2), 180px)。
- 水平居中固定宽度的表单列；
  纵向不再因内容总高变化重新分配位置。
- 低高度窗口自然滚动；
  不硬裁切、不将错误绝对定位盖住字段。
- Footer 跟在完整表单后32px，
  与表单保持关系。

在实际字体与内容下微调上述起点，
但 idle、checking、unconfigured、waiting、failed
在同一视口使用同一个起点。

### 5.2 明确状态消息的位置

Provider区域下保留40px、
两行13/20文字的简短状态区。

初始可以展示“通过系统浏览器安全登录”；
状态变化在同一区域替换。

状态区采用“可伸缩文字＋右侧动作”的一行布局：

- 文字最多两行。
- 取消/重试为24–32px高的安静操作。
- 附加技术原因放入关联诊断Popover/Dialog。
- 主表单不容纳整段开发配置文档。

关键错误摘要始终完整、可见；
详情层承载附加技术信息，
不裁切用户必须知道的原因。

邮箱错误放在密码字段之后、提交按钮之前。

标题和两个输入框的位置因此保持稳定；
更长错误只向下扩展操作区。

字段格式错误就近标识，
提交失败保留输入并给出明确重试。

状态提示使用适当live region；
仅在用户提交产生错误时转移到合理错误位置，
不在每次后台检查时抢焦点。

### 5.3 验收方法

同一1440×900视口、
字体加载完成、滚动位置不变时，
记录标题、邮箱框、密码框的bounding box。

从idle切换到provider未配置、超时、网络错误：
这些元素的顶部变化不超过1 CSS px。

邮箱错误显示时：
标题、邮箱框、密码框不移动；
提交区允许在内容确实变长时向下扩展。

同时测试：

1280×800、960×720、
注册、长中文错误和键盘焦点。

内容过长时能滚动到全部操作，
不能用固定高度隐藏消息。

## 6. 第五阶段：把登录左侧重新设计成一张完整画面

本轮保持“平面色块水岸”方向，
重做实际造型和图文关系。

当前SVG中几块分离的封闭色片只是旧草稿，
不再作为必须保留的轮廓。

### 6.1 完整构图先确定

左栏内部只保留两组：

1. 顶部品牌标记，边距24px。
2. 一个整体的艺术内容组，包含风景和标题。

艺术内容组最大宽600px，
左右安全边距40–64px，
在剩余区域内整体居中。

风景与标题在同一个排版组中，
不分别使用 flex:1 和贴底规则。

1440×900下的视觉目标：

- 实际有色风景宽约480–560px、
  高约250–310px。
- 实际有色轮廓的下边缘到标题顶部为28–40px。
- 图文整体位于左面板中部略偏下，
  与右侧主要表单形成视觉平衡。
- 标题36/42、最多两行，
  左对齐于画面主体的明确轴线。

“实际有色轮廓”不是包含巨大透明边的SVG画布。

检查SVG的painted bounds与viewBox，
让图文距离由真正可见内容决定。

必要时调整viewBox/内部留白；
保持缩放比例，不拉伸画面。

### 6.2 形状必须组成一个连贯水岸

采用“近岸围合水面、远山位于水面后方”的单一景别：

- 水面是连续空间的一部分，
  其边缘由岸线和画幅共同限定。
  移除当前两侧斜切、下方封闭的“板材”观感。
- 近岸与水面接壤并有清楚遮挡。
  不要让暖色岸块与水面之间
  留出一条无来源的背景缝。
- 远山采用一个主要峰势和少量次级转折，
  有大中小的节奏；
  不是等高、等宽的连续波浪。
- 深色结构属于近岸的阴影、植被或前景质量，
  用于组织画面；
  不能作为独立漂浮的小补丁。
- 倒影与光带的位置服从水面方向。
  倒影保持水平，长度和间隔有关系，
  不随意散落四条线。

保留简洁平面形式，
避免重新做写实湖景。

简单不是减少到三个模板几何形；
必须在层次、遮挡、重心和曲率上作出设计。

沿用现有艺术色系作为起点：

场地：#EDF0E8
远山：#D6E0D7
水面：#7B969B
岸线：#BC9670
深结构：#344D48
少量光：#C39448

可以在艺术域内调整明度和面积比例，
使远山可辨、深结构有支撑、暖色不过分抢眼。

UI功能色不随插画逐页变化。

### 6.3 用完整页面判断美术，而不是靠路径数量验收

在实际认证页内完成静态构图校准，
先关闭动画检查：

- 缩到25%仍能辨认前后和主要水岸关系。
- 原尺寸没有“几块色片分别摆放”的感觉。
- 插画与标题是一组，
  Logo是品牌入口，
  右侧是实际操作区。
- 去掉文案解释，
  画面仍能被理解为自然空间，
  而不是只能靠waterside文件名辨认。

完成一套推荐方案后再进入动画。

静态目标保存在本轮记录中，
后续路径与参数根据它落实；
不要先把未经验证的坐标写成不可改变的规范。

有可用美术工具时可以用于原创构图，
但最终需要可本地运行、可局部动画的分层资产。

参考图片只用于分析，遵守原资产授权。

### 6.4 深色模式有自己的画面关系

左侧不能在深色模式下继续占半屏的高亮浅底，
而不作设计判断。

为同一SVG建立深色艺术变量：

背景接近产品深色底面，
山、水、岸保持前后层次。

调整的是明度和饱和度，
不把整张图透明化或统一invert。

标题与Logo切换到适合深底的颜色。

浅色和深色分别保存整页图，
检查两侧亮度是否协调。

### 6.5 动效只发生在有自然含义的层

- 主山体、岸线、整体图框稳定。
- 倒影局部水平移动：
  完整往返16–20 SVG单位，
  6–8秒周期。
  2秒连续观察能看出变化，但不抢表单。
- 输入聚焦时局部光带220ms内变化；
  不是整幅图转头。
- 真实提交/授权等待时，
  光带沿水面方向缓慢通过遮罩，
  不作为假进度条。
- 成功后可有一次短收束，
  实际导航立即执行。
- 失败由表单表达，
  风景不抖动、不整片变红。
- reduced motion、离屏和原生最小化保持静态，
  登录功能不受影响。

艺术组件只接受展示状态枚举，
不接收密码、输入内容或账号对象。

## 7. 第六阶段：核对真实配置，精修完整应用

### 7.1 区分当前用户外观与测试新默认

只读核对实际profile中的：

主题、强调色、侧栏尺寸、
页面缩放、构建标识。

业务内容不进入公开证据。

用同样配置建立隔离TEST profile复现。
不能拿全新Forest截图代表保留Iris的用户环境。

外观设置增加清楚流程：

预览统一默认外观 → 采用 / 取消 / 恢复原选择。

预览退出恢复原值，应用后持久化；
不通过删除localStorage强制迁移。

检查所选强调色影响的：

链接、Focus、Selected、Hover

是否成套协调。

主操作、语义状态和用户强调色的职责保持明确，
不出现紫色Focus、绿色选中、
第三种颜色按钮随机混搭。

### 7.2 把视觉参数落实到组件家族

保留现有字体资产与已校准角色，
本轮重点清理同类控件仍各自设置的差异：

- 标准按钮36px。
- 工具Trigger32px。
- 认证控件44px。
- 普通UI控件13/18或14/20。
- 正文15/24。
- 辅助文字12/18。
- 控件圆角8px。
- 菜单/内容面12px。
- Dialog16px。
- 控件内图标与文字按同一光学组合校准。

将项目属性触发器、列表头、原生选择器、
菜单和设置中的局部旧规格归到对应角色。

保留必要例外的语义说明，
不做纯数字替换。

检查实际computed styles，尤其：

字体简写、内联变量、旧上游样式的覆盖。

深层override、测试属性选择器和不断增加的!important，
要在真实组件边界收敛。

文字、边框、内边距和动作反馈共同校准。

不能只把7px圆角改成8px，
就宣称质感改善。

### 7.3 当前主要交互继续验证

实际入口包括：

Active、Display、Project details、
项目标识、账号设置、来源面板、目录操作。

检查：

- Pressed/Open/Selected/Focus分别可辨。
- 完整控件表面反馈。
- 浮层退出不留遮罩。
- 快速开关不中断正确操作。

登录状态错误首先修状态和布局，
不用延长transition掩盖跳动。

已有真实菜单、父子Escape、
阅读锚点、草稿与确认保护保留。

## 8. 第七阶段：收敛剩余卡顿

使用同环境、同数据、同窗口，
测量三轮生产构建：

- Project details冷首次。
- 长会话返回。
- Active/Display各30次热操作。
- 32文件Diff首开和文件切换。
- 登录艺术运行期间的逐键输入及第三方状态切换。

当前记录中Project details冷首次与长会话返回约104–128ms，
作为排查线索，不冒充当前每次实测。

分别记录：

按下反馈、可操作、数据稳定、动画完成。

trace定位脚本、订阅、格式化、列表处理、
布局和绘制的真实开销。

可见反馈以约100ms内为目标；
重内容准备与动画时长分别报告。

保留完整任务数据与动画，
修复造成延迟的路径，
而不是关功能跑分。

如果只有某一轮变快，
记录全部轮次并继续定位。

最终保留测量环境、样本数、原始数据和剩余慢路径，
不用少量浏览器采样宣称全平台60fps。
