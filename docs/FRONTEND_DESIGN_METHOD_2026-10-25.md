## 2. 先定义我们自己的产品组织方式

核心场景固定为：查看成员活动 → 阅读有证据关联的会话 → 核对文件差异 → 查看检查点或恢复预览。

每个场景持续回答五个问题：谁的工作区、正在看哪项工作、哪些文件真的变了、关联上下文是什么、这份状态存在哪里且能否恢复。

建议的内容层次：

- 项目提供边界；成员与设备说明来源，不让设备内部编号占据阅读主位。
- 活动摘要用于扫描。可按有明确依据的会话或检查点聚合，原始消息和文件明细可展开；不能按时间接近伪造因果。
- 会话解释工作上下文，差异提供文件证据，检查点提供状态与恢复范围。三者保持清楚的关系与独立性。
- 任务只在存在真实绑定时作为关联项；缺少关联明确显示未关联。
- 本地已捕获、等待共享、后端已接收、异地备份已验证分别表达。Agent 运行状态、同步状态和备份状态不能共用一个含糊的“正常”标志。
- 恢复是进入明确范围的操作流程：选择检查点 → 查看影响目录与文件 → 确认 → 结果/失效处理。队友记录不提供越权恢复按钮。

这些是待样板验证的信息设计建议，不是对现有界面完成度的描述。

## 3. 制作顺序与交付门槛

| 步骤              | 具体工作                                                                           | 进入下一步的证据                                                           |
| ----------------- | ---------------------------------------------------------------------------------- | -------------------------------------------------------------------------- |
| A. 运行基线       | 使用真实本地账号与授权测试目录，操作活动、消息、差异、历史和恢复预览；记录缺失链路 | 每一步的实际截图、可用/缺失状态和可复现操作；不以历史报告代替              |
| B. 拆解体验       | 追踪导航、选择、分页、滚动、弹窗、焦点、快捷键、面板、状态文案各自的源码与数据契约 | “行为 → 源码 → 当前接入情况 → 验收方法”的清单；不能只列 Button/Dialog 名字 |
| C. 定共同场景     | 固定对象、数据、状态与允许的操作；写清会话/检查点的证据关系                        | 三方案用同一份数据和选择状态，同一任务可完成，同一关键信息可获得           |
| D. 做三套完整样板 | 在隔离入口复用行为层，分别实现完整导航、列表、阅读区、差异、检查点、菜单与状态表达 | 每个方案可走完整核心场景；不能仅展示首页或独立组件墙                       |
| E. 共同验收       | 按相同脚本操作，检查规定尺寸、复杂内容、焦点、滚动、失败恢复与桌面运行             | 对比截图、问题与修复记录；技术通过与视觉判断分别报告                       |
| F. 用户选择       | 展示方向差异、实际取舍和建议，不自动替换现有产品                                   | 用户选定方向后再建立正式规范并迁移其他页面                                 |

设计不是“第一屏画完再补状态”。普通、选中、悬停、焦点、禁用、加载、空、失败、离线、权限变化都属于组件及流程设计的一部分。

## 4. 三个可比较的方向

以下是工作假设，不是已选定的外观。三个方向均保留同一核心流程和全部重要信息；各自的默认重心不同，不隐藏功能来制造整洁。

| 方向     | 主工作区与信息组织                                                                   | 排版、密度、表面表达                                                            | 收益与代价                                                         |
| -------- | ------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------- | ------------------------------------------------------------------ |
| 协作脉络 | 按实际关联聚合活动；成员、工作摘要、变化范围可横向扫描，展开后阅读上下文和文件证据   | 紧凑且对齐的行、稳定的元信息列；连续列表以分组和细边界组织，选中态突出当前位置  | 便于同时掌握多人进展；连续读长会话需要进入阅读区域                 |
| 会话阅读 | 选定工作后以完整上下文为主，相关差异与检查点保持可定位；成员活动作为可恢复位置的索引 | 中等密度、适合中英混排的阅读宽度，用户/Agent/工具内容分层；代码区保持独立的密度 | 便于理解过程和交接；初始视口展示的活动行较少，不能删除其他成员信息 |
| 改动核对 | 文件与差异成为主工作区，固定上下文区域解释来源，会话和检查点可按关联定位             | 文件名、行号与状态严格对齐；高密度操作栏与宽代码区，边界服务于比较和选择        | 便于评估代码影响；长会话需要切换到阅读状态并保留原定位             |

每个方向必须同时确定：中文/英文/代码的排版关系、主次信息节奏、表面层次、选择与焦点的区别、导航与操作分级、列表/消息/状态的表达。不得仅通过配色区分。

## 5. 工程实现边界

沿用当前 React、原生 store/路由、Radix 交互基础、差异渲染和桌面框架。实际组件依赖以完整上游 `packages/web/package.json` 为准，不能只看根目录的旧前端依赖。

实验由一套共享场景模型与行为控制，加三种组合布局和限定作用域的样式构成。复用现有真实读取接口；缺失接入以明确的测试适配器演示，并逐项注明。不能给三种方案复制三份业务请求和恢复逻辑。

从任务提炼必要的产品组件，例如活动摘要、成员/Agent 来源、会话阅读区域、文件变化列表、检查点状态和恢复范围。它们共同工作，不能用“做了两个漂亮组件”替代整条流程。会话组件先评估与当前捕获会话的数据契约是否兼容；优先适配既有渲染和滚动行为，避免伪造可执行原生会话。

实验主题挂在各方案根节点；浮层通过实验专属容器或主题作用域继承，避免 Portal 跳出后样式失效。不得改全局主题影响原工作台。图标先沿用同一家族；如需比较候选，仅在实验内比较一小组真实功能，正式选择后统一映射。

所有新增源码留在 owned integration，按现有准备脚本生成运行副本。保留上游版权、未提交内容和现有正常启动入口；不 reset/clean/stash，不创建提交。

## 6. 公平比较与复杂状态

固定一份明确标记的测试场景：三位成员、手动修改、Codex 记录及另一 Agent 的明确测试记录；长中文任务名、中英混排、长路径、多文件新增/修改/删除、长回复、代码块和差异。第二种 Agent 的测试内容不代表已经支持真实采集。

普通场景与压力场景共用固定 ID、顺序和内容。三种方案切换时保持相同成员、活动、会话、文件及检查点选择。流式行为通过同一明确标记的回放源输入，不调用付费模型；不能把回放描述为真实 Agent 正在工作。

比较提供两种方式：原版与方案的同状态并列图；可操作的完整尺寸方案切换。不得把两个 1440 宽工作台硬挤进一个 1440 宽窗口，再拿被压坏的布局判输赢。

| 检查                               | 必须观察的行为                                                                               |
| ---------------------------------- | -------------------------------------------------------------------------------------------- |
| 1280×800、1440×900、窄详情面板     | 无控件遮挡/碰撞，长路径能识别并访问完整值；重要操作不因缩窄消失；不靠缩小全文字号            |
| 活动 → 会话 → 差异 → 检查点 → 返回 | 当前对象及来源明确，关系有证据，返回恢复选择和阅读位置；记录操作次数与基线差异的理由         |
| 阅读历史时到达新内容               | 不抢滚动；提示有新内容；用户主动返回末尾才继续跟随；加载旧消息保持阅读锚点                   |
| 菜单、弹窗、键盘                   | 键盘可达、焦点可见、Escape 只关闭当前层、关闭后回到触发处；浮层不被裁剪                      |
| 加载、空、失败、离线与权限撤销     | 说明影响和可做的下一步；不把错误渲染为空内容；撤权后不保留可读缓存                           |
| 检查点与恢复                       | 已捕获/已共享/异地已备份不混淆；失效预览不能确认；队友目录不被写入                           |
| 原版与桌面回归                     | 实验样式不影响正常路由；在真正桌面窗口检查字体、缩放、面板和弹窗，不将浏览器截图冒充桌面验证 |

实际执行项目要求的 typecheck、tests、build、integration typecheck 和必要的真实验收。测试只能证明具体行为，不能证明审美已达到目标；最后的视觉方向仍由用户实际比较后选择。

## 7. 交付与完成定义

交付应同时包含：基线与缺口清单、三个可操作完整场景、同内容对比截图、每个方向的取舍与问题、实际检查结果。只有文档、截图或主题变量都不足以完成样板任务。
